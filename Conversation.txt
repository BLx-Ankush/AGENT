Build a privacy-preserving AI vision/browser agent that can understand what is happening on a user's screen and perform browser actions, while preventing sensitive information from being sent to the cloud.

User's Browser
→ Local vision model
→ Understand screen/UI
→ Detect sensitive information
→ Redact PII/passwords/faces/etc.
→ Send only sanitized context
→ Cloud/server LLM/VLM reasons about task
→ Returns action
→ Local browser agent executes it

The problem specifically mentions technologies such as WebGPU, WebAssembly, ONNX Runtime Web and Transformers.js for running lightweight models locally.

other PII
Send the sanitized visual context to an LLM/VLM.

Problem Statement Title	
On-device Visual Perception for Light-weight Browser Agents
Description	
Background AI agents are becoming omnipresent in the current era and can play an important role in our digital interactions. If an agentic AI pipeline has access to our visual context, screen states, they can assist users in complex workflows and automate many tasks. Most of the agentic AI pipelines are deployed on server side which limits the type to data that a user can share with it. It would open a new dimension of possibilities, if a local agent is deployed on user machine particularly browser which can eliminate the need to share the sensitive data with the server. Local system generally has fewer resources than server and is unable to host a full-fledged pipeline therefore only the non-sensitive data such as structure of the screen, application fields etc can be sent to server for processing.

Modern browser APIs (such as WebGPU and WebAssembly) and local inference libraries (like ONNX Runtime Web and Transformers.js) have unlocked the ability to run lightweight machine learning models directly on the client. The aim is to bridge these two environments: leveraging the reasoning power of cloud or server based AI while strictly enforcing data privacy at the client side.

Description Participants are required to build a privacy-preserving vision agent which runs on browser. This involves implementing a client-side architecture where a local Vision Transformer (ViT) or equivalent computer vision model 'reads' the user's screen and takes decision based on that. If it requires the visual context to be sent to server, it shall sanitize the sensitive/PII data using DOM tags or any other method, before any network request is made. It should dynamically detect and redact sensitive elements. For example, blurring faces, blacking out passwords, and masking PII etc. Only this anonymized, unidentifiable data should be transmitted to the central server which should be aware for this redaction scheme and can process data accordingly. The server will then process the sanitized context and return actionable commands for the browser agent to execute. Participants must balance the trade-offs between inference latency and the accuracy.

Expected Solution A successful submission should include a working prototype consisting of client side extension and server that demonstrates the following:

Client-side (extension/JS) running in popular browsers (chrome, Firefox) components:

• Local Vision Processing: Implementation of a client-side vision model running in the browser (e.g., via WebGPU) that evaluates the current screen state.
• Privacy Preserving Filter: A mechanism for sanitizing sensitive or personal visual data. This can be achieved through local bounding-box redaction, semantic obfuscation, masking etc. This should be clearly demonstrated.

Server-side implementation components:

• Server Side Integration: The transmission of the anonymized visual context to a centralized LLM/VLM, which successfully interprets the sanitized data and returns the response which may be processed data to be again ingested by local client or an UI action (e.g., 'click the submit button,' 'scroll down') that the local client executes.
• Participants are free to use any offline deployable (open-source/open-weights) model on server side. During SIH they can use cloud hosted version of these. An end-to-end task assisting the user should be demonstrated.

Don’t let the poster alone trigger panic. I looked at it closely.

Yes, there is substantial surface-level overlap with what we are building: on-device perception, browser screenshots/DOM, local PII detection/redaction, sanitized payload to a cloud VLM, and browser-agent execution.

But the important question is what is actually implemented and how deeply the two systems solve the problem.

Where their poster appears to stop

Their visible pipeline is essentially:

DOM heuristics → on-device detection → redaction/masking → frame optimization → VLM reasoning → structured action plan → browser executor

That is a legitimate implementation direction, but it is a fairly direct interpretation of the PS.

Where your system has a materially different architecture

Your implementation has a much stronger privacy-control-plane concept:

Browser capture → local multimodal perception → unified scene graph → privacy classification → tokenization/local vault → sanitized state → independent egress verification → cloud reasoning → action validation → local authorization/confirmation → exact target execution → outcome verification/re-observation

The important differentiators are not the words "PII detection" or "on-device vision." Those are expected in this PS.

Your defensible differentiators are:

1. Privacy firewall / fail-closed egress

The cloud doesn't merely receive a redacted screenshot. Every outbound payload goes through an independent verifier that can reject transmission.

2. Tokenized private-data architecture

Instead of simply deleting private information, your system can represent it as things like:

<EMAIL_01>
<PHONE_02>
<SECRET_01>

and resolve the real value locally at execution time through the token vault.

3. Exact target identity

Your P0-B work specifically addresses the dangerous problem of:

"The agent observed one element, but the executor acts on another."

The harvested DOM element is mapped directly to the execution registry rather than reconstructing the target independently.

4. Authorization before execution

Your architecture treats:

observation → target identity → binding → authorization → confirmation → execution

as a security chain, rather than just letting the agent produce an action plan.

5. Event/risk-aware perception

You are not proposing expensive vision inference on every browser frame. The scheduler decides whether perception is needed and escalates from:

DOM/A11y → lightweight CV/OCR → heavier local vision

based on risk.

6. Visual + structural unified representation

DOM tells you what structurally exists; vision tells you what the user actually sees. That matters for things like canvas/WebGL, rendered documents, images, revealed secrets, etc.

The biggest mistake your team can make now

Do not try to beat the senior team by adding random features.

That creates a bloated project and weakens the demo.

Instead, make your core story extremely clear:

“We are not merely redacting screenshots. We are building a privacy control plane between the browser and the AI agent.”

Then demonstrate something that makes that architecture obvious.

For example:

Private value exists visually → local perception detects it → it becomes <SECRET_01> → cloud receives only sanitized representation → agent decides an action → local vault resolves the secret → action executes only after authorization.

That is much more compelling than simply showing a red rectangle over PII.

And about them being seniors

Their year of study is essentially irrelevant to the technical question the jury will evaluate.

A senior team can have a polished poster and still have a simpler implementation. A junior team can have a technically deeper system. The jury ultimately gets to see the working prototype, architecture, engineering decisions, and evidence.

So I would tell your teammates:

“We are not competing against their poster. We are competing on what our system can demonstrably do.”

The issue

The implementation stores only:

_invalidatedObservationId: string | null

That means it remembers only the most recently consumed observation.

The commit's own test confirms this:

OBS_N  → invalidated
OBS_N1 → invalidated

OBS_N  → isObservationStale() === false
OBS_N1 → isObservationStale() === true

So an old observation can become reusable after a later observation is invalidated. That's contrary to the stronger invariant:

An observation that authorized a state-changing action becomes permanently invalidated for the lifetime of that session.

This is especially relevant to replay/caching attacks:

OBS_N
  ↓

  ↓
OBS_N invalidated

OBS_N1
  ↓
ACTION_B
  ↓
OBS_N1 invalidated

attacker replays OBS_N
  ↓

The existing checkActionFreshness() may reject some replay paths, but P1-G's own observation lifecycle gate no longer guarantees permanent invalidation of OBS_N.

_invalidatedObservationIds: Set<string>

after successful state-changing action
    → add(observationId)

new capture
    → if set.has(observationId)
       reject

replay OBS_N → MUST STILL REJECT
